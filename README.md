### 一个给长期在线的 AI 用的记忆架构

> **怎么装**
>

## 一、起点

有天早上，我问它："昨天说的那件事，定了吗？"

它答得很顺，语气也对，但内容全是它自己编的。

那种感觉很奇怪——它不是在骗我，它是真的不知道。它只是**接得很自然**。
它越想显得没忘，就越像忘干净了。

后来我去翻聊天记录，翻到了昨天的那几句。**东西一直在那里，只是不在它眼前了。**

那天我才想明白一件很别扭的事：

> **AI 的记忆问题，从来不是"它忘了"，是"它不知道自己忘了"。**

---

## 二、第一个判断，是错的

我一开始的想法很朴素：**那就让它记得更多**。

加长上下文、多塞记忆、把重要的事反复提。我做了一版又一版，效果都很微妙——**它好像记得，又好像不记得**。

直到我把参数翻出来看：

```
上下文窗口      1,000,000 token
压缩触发阈值    80%（八十万 token 才会压成十六万）
一天聊天        687 轮 / 20 万字 ≈ 32 万 token
```

**三十二万，连窗口的三分之一都不到。** 剩下那六十多万是空的。可它还是会忘。

那一刻我明白自己一直在修错的东西。

---

## 三、真正的瓶颈不是容量，是注意力

我做了一个很土的试验：把 200 条记忆一起塞进去，让它自己挑。

结果它认真看了前 20 条，剩下 180 条**在上下文里，但等于不在**。

```
塞 200 条  →  只认真看前 20 条
剩下的 180 条：占着位置，不参与判断
```

所以"多记一点"这条路从一开始就走不通。**问题不是装不下，是装进去也白装。**

推论很直接：**要解决的不是"怎么装更多"，是"怎么让进去的那一点点真的对"。**

---

## 四、人是怎么记得的

我想了想人是怎么过日子的。

人也会忘。但人的忘有个特点：**忘了的东西，通常能找到回来的路**。
你忘了朋友姓什么，但你知道去翻通讯录；你忘了去年哪天去的医院，但你知道去翻病历。

**人不是记住了一切，人是留了索引。**

于是问题就变形了：

> 不是"怎么让它记得更多"，
> 而是"**怎么让它忘得有结构，需要时还找得回来**"。

## 五、为什么是"块"，而不是别的东西

这是整套东西的地基，所以先把另外三条路否掉。

### 5.1 三条被否掉的路

**① 向量检索（embedding + 最近邻）**

它擅长"语义相近"，但我们要的是"就是那一件事"。

```
问："上次说的那个忌口是什么？"
向量给你的：一堆"看起来像在聊吃东西"的段落
我们要的：  "他讨厌香菜" 这一句
```

更致命的是代词——"上次说的那个"，**连一个关键词都没有**，向量也只能给你一堆"氛围相似"的东西。
而相似的邻居里，常常混着**完全相反**的事实（喜欢香菜 / 讨厌香菜，向量距离几乎是零）。

**② 摘要压缩**

把一天压成三百字，读起来很顺。但"那杯奶茶 19 块""他生日 12 月 8 号"这种细节，压完就没了。
而用户最会追问的，恰恰是这些。

**压缩是有损的，且损失不可预测** —— 你永远不知道被压掉的是不是明天要用的那一条。

**③ 知识图谱（实体-关系-实体）**

听起来最"结构化"，实际上撑不住口语。真实对话里 66.6% 的句子没有主语（中文口语就是这样），
抽出来的图会有一半是悬空的节点。

而且图一旦建错，改一个节点要动一整片，**错一次污染一片**。

### 5.2 那为什么是"块"

因为**块是唯一同时满足三件事的最小单位**：

```
① 足够小 —— 一块 150~250 字，能塞进任何预算
② 足够完整 —— 一块=一件事的一个侧面，单独拿出来有意义
③ 足够笨 —— 不预设结构，什么都能装（一句话、一个订单、一个偏好、一次决定）
```

**关键在第三条**：块不带结构。它不是"实体",不是"三元组",不是"向量"。

它只是**一段被时间戳和几个特征词标记过的原文**。
正因为它笨，它才装得下人类说话那种没有形状的东西。

> **块 = 一张从桌上收走的纸。上面写了什么就是什么，不加工、不解释、不合并。**

### 5.3 一块为什么装不下全貌（这是设计，不是缺陷）

一张卡一百多字。它装不下"那杯奶茶到了没、多少钱、几点点的"。

**这是故意的**：

```
如果一块能装下全貌 → 它就得是一篇摘要 → 回到"摘要丢细节"那条死路
所以一块只能装一件事的一个侧面
→ 而"一件事"往往散在好几块里
→ 所以答案是"拼出来的"，不是"找出来的"
```

代价是检索要多抽几张、要聚线、要拆槽。但换来的是：**细节从来不丢。**

## 六、库的原理：三层，而且顺序不能反

块不是扔在一个桶里。它有三层，而且**这三层的职责和写入顺序都是焊死的**。

```
                    ┌───────────────────────────┐
   ③ 索引（8 张）    │ 特征→块 / 时间→块 /        │  纯派生，可删可重建
                    │ 类别→块 / 话题→块 / ...    │  ← 丢了无所谓
                    └────────────▲──────────────┘
                                 │ 从块库派生
                    ┌────────────┴──────────────┐
   ② 块库（blocks）  │ 347 张卡片，每张带       │  当前视图
                    │ coord / ver / origin_at   │  ← 坏了可重建
                    └────────────▲──────────────┘
                                 │ 从账本重建
                    ┌────────────┴──────────────┐
   ① 账本（events）  │ 只追加，永不改，永不删     │  唯一真相
                    │ 每一笔都带 seq + hash     │  ← 它坏了才是事故
                    └───────────────────────────┘
```

### 6.1 账本：只追加的事件日志

每一次建块、覆盖、重建，都往 `events.jsonl` 追加一行：

```json
{"seq": 1024, "ts": "2026-10-27T20:15:03+08:00", "type": "BLOCK_WRITE",
 "coord": "1-1-42", "payload": {...}, "prev_hash": "9f8e", "hash": "a1b2"}
```

三条性质：

```
① 只追加 —— 打开文件只能 write 末尾，不能改、不能删
② 全局单调 seq —— 不是每个会话各自从 0 数（这条我踩过坑，见第十二节）
③ 带 hash 链 —— 每一行指向前一行，改了就能被验出来
```

**它存在的唯一目的：让上面两层随时可以扔。**

### 6.2 块库：账本的一份"当前视图"

把账本重放一遍，就得到块库。所以块库是**可以整份删掉重建的**。

这就是为什么可以放心地"重建索引""重排""迁移格式"——
因为在这些动作底下，账本一动不动。

### 6.3 索引：8 张纯派生的目录

```
feat.json    特征 → [块]
gate.json    门类 → [块]
time.json    按天分桶 → [块]
topic.json   话题 → [块]         ← 判重/覆盖用
chain.json   链（同一件事的多块）→ [块]
origin.json  源头 → [块]
```

索引可以随时全量重建（`node src/cli.mjs rebuild`）。
**索引坏了不是事故，只是慢一次。**

### 6.4 为什么写入顺序不能反

```
正确：  先算 → 先写账本 → 再写块库 → 最后重建索引
错误：  先改块库 → 再补账本
```

**反一次就是永久损失**：如果块库改了、账本没记，那这段记忆在"重建"的时候会凭空消失。
我踩过这个坑——三天后档案室被一次错误合并弄坏，想重建才发现**账本里没有那一段**。

**所以从那天起，顺序焊死：先账本，后档案室。一次都不许反。**

## 七、建块的原理

### 7.1 什么时候建（为什么不是每轮）

我最初打算"每聊一句就记一笔"。算了一下：

```
一天 687 轮 → 345 块/天 → 一年十二万块
```

不是装不下（1 个 T 能装几百万块），是**碎到没法用**：
十二万张卡片里，任何一张单独拎出来都只有半句话，检索时全是噪音，拼也拼不起来。

所以真正的时机只有一个：

> **内容要离开桌面的那一刻。**

具体是四个触发：

```
① 上下文要压缩时     ← 最精确（这段马上要消失，赶紧做成卡片）
② 会话归档 / 换人时
③ 换日 00:00
④ 上下文占用过 25~30%（低水位，提前动手）
```

目标产出是 **40~60 块/天**，不是 345。

### 7.2 怎么切（一件事一块，**交给模型切**）

一轮对话经常混着三件事：

```
"奶茶到了没？……对了那个架构定了吗？……还有显卡插不上"
```

**一块塞三件事 = 三件事都检索不准。** 所以建块前要先切。

**早期版本用正则按句子切，实测不够用：**

```
· 多人刷屏被切成半句：一块"…在吗"，一块"她回：在在在" —— 各缺一半，谁也读不懂
· 一句话里夹两件事："换成了 SnowLuma，另外明天再修姐姐那台机器" → 一块两件事
· 反向失败：整段两百字的群聊被塞成一块，检索命中的永远是这块大杂烩
· 正则猜主题（谓词 + 后面几个字）会拼出「主人|能力|_」「主人|状态|2026」这种垃圾键
```

**现在让模型切**（`src/ai.mjs` → `segmentWithAI`）：把一段话交给 llm，让它输出
"一条一件事"，顺带给每块 **标题 / 特征词 / 归属 / 类型**。

```js
import { addBlocksFromText } from 'beme/write'

await addBlocksFromText(一段话, {
  llm: async (prompt) => 你的模型(prompt),   // 任何模型都行，只要求"给字符串回字符串"
  aboutName: '主人',
  sourceId: 'chat:2026-10-29:001',
})
```

三条硬规矩：

```
① 每块都走 noTopic —— 一件事一个坑，永远不会把别人的内容挤掉
② 模型只负责"切"和"起标题"，**不许造特征词**：特征只能从词表里挑，
   否则检索端对不上（模型造的词不在索引里，等于白抽）
③ 模型不可用 / 输出不是 JSON → 自动退到正则切句，不报错（只是粗一点）
```

**噪音不是靠清洗，是靠切得够细。**

### 7.2.1 坑键：别让两件事抢一个坑

早期用「主语|谓词|宾语」拼 topic，靠它找"同一个坑"。实测会撞车：

```
两件不同的事拼出同一个 topic「主人|状态|vol2」
→ 第二件覆盖第一件 → 一个坑被覆盖 15 次，最后留下的是**别人的内容**，
  而 source 还写着第一件事 —— 检索把错的当对的，且不报错
```

现在的规矩：

```
① topic 优先用 source_id 派生的稳定键（`src:<source_id>`），不猜
② 需要"一件事一个坑"时传 noTopic: true，永远新开
③ 判"是不是同一件事"可以交给模型（sameEventWithAI），模型不给就用特征重合度，再不行一律新开
```

> **判错成"覆盖" → 静默指错；判错成"新开" → 只是多一张卡片。空间最便宜。**

### 7.3 三种出厂状态

```
ROOT       全新的一件事，开一个新坑
OVERWRITE  同一件事的新版本：ver+1，coord 不变，origin_at 不变
REBUILD    话题一样但语义变了：开新坑，旧块 head 指向新块
```

判"是不是同一件事"只有一条准则：

> **判不准的时候，一律新开。**

```
判错成"覆盖" → 所有索引都指向错的答案，而且不报错（静默指错，最可怕）
判错成"新开" → 只是多一张卡片，空间是最便宜的
```

## 八、按门类分词

这一节是整套东西**最容易被跳过、但跳过就全错**的地方。

### 8.1 为什么非得分词

原始文本没法比。"那杯奶茶多少钱"和"19 块"，字面重合度是零，但它们说的是同一件事。

所以要先把文本变成**可比的东西**——特征（features）。

而中文的分词有两个麻烦：

```
① 没有空格，切法本身有歧义
   "南京市长江大桥" → 南京/市长/江大桥？ 南京市/长江大桥？
② 同形异义
   "苹果" 可能是水果，可能是公司，可能是手机
```

### 8.2 所以不能全局分词，要**按门类分词**

**门类**（gate）= 这段话属于哪个大领域。我先定了一套：

```
R  人际（谁、关系、称呼、约定）
T  技术（机器、项目、代码、配置）
L  生活（吃、住、行、买东西）
H  健康（身体、睡眠、情绪）
W  工作（任务、进度、钱）
C  创作（画、文、设计）
...
```

数量有限（十几个），**判得准**，而且**判错代价可控**（判错门类只是找不到，不会给出错答案）。

**按门类分词的意思是两件事：**

```
① 先定门类，再在这个门类的小词表里抽特征
② 特征只在自己的门类里有意义，不同门类的同名特征不互通
```

举个最典型的：

```
"苹果多少钱？"
  → 门类 L（生活/购物）→ 特征：苹果、斤、水果、价格
  → 命中的是"上次买苹果 5 块一斤"

"苹果多少钱？"
  → 门类 T（技术/设备）→ 特征：苹果、MacBook、配置、价格
  → 命中的是"他在看 MacBook Air 的价格"
```

**同一句话，两个门类，两份词表，两条完全不同的答案。**

如果只做全局分词，"苹果"这个特征会把这两个场景**串在一起**——
用户问水果，AI 回了一堆电脑配置。**这是纯关键词检索永远修不好的病。**

### 8.3 两层结构是怎么配合的

```
            一句话
              │
       ┌──────▼──────┐
       │ ① 判门类     │   规则先给候选（命中谓词词表）
       │  （gate）    │   拿不准就交给 AI 判（只判一次，判完存档）
       └──────┬──────┘
              │ 得到 R / T / L / H / W / C
       ┌──────▼──────┐
       │ ② 门类内分词 │   在**这个门类的词表**里抽特征
       │  （feat）    │   抽不到就记"无特征"（不是错误，是正常）
       └──────┬──────┘
              │ 得到 ["奶茶","订单","沪上阿姨"]
       ┌──────▼──────┐
       │ ③ 落块       │   features 只存名字，不存编号
       └─────────────┘
```

检索时反过来：查询也走同样两步，然后**门类作为硬过滤**（先挡掉 80% 的错配），再在剩下的候选里比特征。

### 8.4 词表为什么是从 97 个词起步的

因为词表是**长出来的**，不是设计出来的。

一开始我只有 97 个种子词。结果就是：**很多话抽不到特征 → 它说"我不记得"。**

这不是它笨，是**词表的锅**。所以：

```
词表会随使用长大（新词发现：反复出现但词表里没有的词）
前期词表薄 → 大量"不记得" → 这是正常的，不是故障
```

**配套的兜底（必须有，不然早期没法用）**：特征一个都抽不到时，不要直接说"不记得"，
先用内容子串匹配捞一次。宁可能搜到，也别空手。

```js
if (!qFeats.length) {
  // 词表里没有这个概念 → 退化成内容子串匹配
  const hits = all.filter(b => b.content.includes(query))
}
```

### 8.5 两个必须做的清理

**① 泛词：`df/N > 0.15` 的词不算主题，是背景词**

实测：问"光发表情什么意思"，"表情"这个词命中 69/347 块（20%）。

结果注入了一整段"表情包"相关的记忆，AI 跟着**只发表情**，而且越陷越深。

```
一个词如果 15% 以上的块里都有，它就不是"这件事的主题"，是"这个库的背景"。
拿背景当主题检索 = 一定会捞到一大堆无关的块。
```

**注意**：要加绝对数量门槛（我设了 df ≥ 10），否则**块少的时候正常词会被误杀**。
（这个坑是我在写自检时踩出来的。）

**② 槽词不进特征**

「几点」「多少钱」「哪里」「什么型号」——这些不是主题，是**要答的空**。

```
"那杯奶茶多少钱"
  → 特征：奶茶、订单        ← 主题
  → 槽：金额                 ← 要填的空
如果"多少钱"也进了特征，那所有带价格的块都会被它拉进来。
```

## 九、检索：不是搜索，是拼装

### 9.1 打分：三个因子

```
score = w1·f1 + w2·f2 + w4·f4      权重 0.3 / 0.5 / 0.2

f1 = 门类命中（主门类 1.0，副门类 0.4）
f2 = Σidf(查询特征 ∩ 块特征) / Σidf(查询特征)     ← 分母永远是查询侧
f4 = exp(-距今天数 / 7)                          ← 距今用 origin_at
```

三个细节都踩过坑：

```
① 分母用查询侧，不用并集
   用并集 → 一块里塞的词越多，分母越大，分数越低 → 会系统性惩罚"内容丰富的块"

② 某因子恒为 0 时必须重新归一化权重
   新库还没有"关系权重"，就不能让它白吃 0.2

③ 距今用 origin_at（这件事最初发生的时刻），不是 created_at（这一版诞生的时刻）
   否则一件半年前的事，昨天被更新了一次，就会显得"很新"
```

### 9.2 可用性铁律：`f2 = 0` 的块一律不许进上下文

这是全套里最重要的一条过滤。

```
门类对了，但一个特征都不沾 → 属于"同类但无关"
这种东西一旦进了上下文，会把真正相关的块挤出预算
```

实测：这条不做的话，问"记忆架构"，注入的会是"奶茶""表情包"。

### 9.3 并列：随机，但可复现

分数完全相同时（分差 < 1e-9），按 `hash(查询文本)` 做随机种子。

```
不用序号        → 否则最早建的块永远赢（一个完美的时间偏置）
用真随机        → 同一句话问两次，答案不一样（不可复现，没法调试）
用 hash 种子    → 既随机，又可复现 ✓
```

**还有一条**：判"有没有把握"不能用绝对阈值。
实测 top8 是 0.843/0.843/0.842……**差 0.001 却全部越过了 0.55 的阈值**。
分数是相对量，必须看**相对差距**（`margin ≥ 0.08` 且 `top1/top2 ≥ 1.10`）。

### 9.4 多抽：K = 12~20，不是只抽 6 张

因为一块装不下全貌（第五节说了），所以必须多抽几张才有得拼。

预算 2500~3000 token。单块超过预算 30% 就截断。

**千万别用 `score/√token` 去选块**——这个公式看起来非常合理（短块信息密度高），
实测把平均块从 191 token 压到 **43 token**，预算只花掉 41%，选出的 6 块**全都不相关**。

### 9.5 聚线与拆槽

**聚线**：同一 `line_id` 的块按 `origin_at` 排成一条链 —— 这是"同一件事"的多个侧面。

**拆槽**：把查询拆成"要答的空"：

```
是否 / 数量 / 时间 / 地点 / 型号 / 谁
```

然后逐个去线上填。**填充不许跨线借词**——把 A 事的数字填进 B 事的句子，是最危险的错法
（填得进去、读得通、但全是错的）。

### 9.6 四态出口（三层判据，必须串联）

```
第1层  分得开吗？   margin ≥ 0.08 且 top1/top2 ≥ 1.10
第2层  分不开：     并列的块是不是同一件事？（最大线占比 ≥ 40% → 是）
第3层  槽齐吗？     要答的空逐个填，缺的列出来

全过 + 槽齐      → 答全（说明这是几轮拼的）
缺槽 / 跨线      → 先答确定的，明说缺什么，然后问用户
坏并列 / 抽空    → 问用户，不许自己挑
确实没有         → 说"我不记得"，不许编
```

**为什么必须串联不能并联**：有次问"这套东西定了没"，它把"是否"这个空填上了，
然后自信地拼出一段完全不相干的内容——**槽齐 ≠ 答对**。

## 十、三级缓存：我们试过，然后全砍了

这一节得单独说，因为**"三级缓存"是所有人做 AI 记忆的第一反应**，而我一开始也做了。

### 10.1 经典三级缓存长什么样

照着 CPU 的 L1/L2/L3 抄，大概是这个形状：

```
L1  最近 N 轮原文         最快，容量最小
L2  近期摘要 / 压缩片段    中速，中等
     ↑ L1 满了 → 摘要后降级进 L2
L3  全量历史（向量库）     最慢，最大
     ↑ L2 满了 → 归档进 L3

读取：先查 L1 → 不中查 L2 → 不中查 L3
```

看起来完美：**热数据在快层，冷数据在慢层，容量无限。**

### 10.2 我们为什么一开始也这么做

因为"记忆"这个词天然让人想到"分层存储"——内存、磁盘、磁带，都是三级。
而且它解决了三个真问题：容量、速度、成本。

### 10.3 为什么最后全砍了

四个理由，每个都是硬伤。

**① 上下文本身就是 L1 + L2**

宿主（任何 LLM 应用）的上下文窗口里，本来就有：
- 最近 N 轮原文（= L1）
- 压缩后的历史摘要（= L2）

**我们再在插件里造一套 L1/L2，等于把同样的东西存两遍。**
一份在宿主的上下文里，一份在我们的库里 —— 然后注入的时候**同一句话出现两次**。

这不是"缓存命中"，这是"自我重复"。

**② 降级本质上就是删**

```
L1 → L2 是摘要  = 丢细节（不可逆）
L2 → L3 是归档  = 丢结构（不可逆）
```

而我们的第二条铁律是"**卡片永不删**"，第四条的推论是"**删不可逆，不翻可逆**"。

**三级缓存的运转机制，就是一台持续删东西的机器。** 它跟这套架构的核心原则正面冲突。

**③ 三层边界会产生"同一事实的多个版本"**

同一个事实：
- L1 里是"他讨厌香菜"（今天说的）
- L2 里是"他不太吃香菜"（上周摘要压扁的）
- L3 里是"他对某些调料敏感"（一个月前的向量）

**读的时候，你信哪个？** 三层各有各的版本，没有任何机制能保证它们一致。
这不是缓存，这是**三个互相不知道对方存在的记忆**。

**④ 写入路径变复杂，而复杂度等于脆弱度**

三级缓存意味着：写入要判"进哪一层"、降级要判"什么时候降"、读取要判"查几层"。

每多一个判断点，就多一个出错的地方，而且**错了不报错**。
（我们的第四条反向纪律：**结构复杂度和脆弱度成正比。**）

### 10.4 砍完剩下什么

砍掉之后，剩下的是**两层，而且其中一层不是我们的**：

```
┌──────────────────────────────────────────────┐
│  热层：上下文（宿主管，我们不碰）              │
│        最近几轮 + 压缩摘要，本来就在那儿        │
│        我们只做一件事：往里面注入一小段        │
└────────────────────┬─────────────────────────┘
                     │ 只在"内容要离开热层"时建块
┌────────────────────▼─────────────────────────┐
│  冷层：块库（我们管）                          │
│        永久保存，只放"已经离开上下文"的东西     │
│        检索时按需捞回几张                       │
└──────────────────────────────────────────────┘
```

**关键收益**：

```
① 不会重复注入 —— 今天说的话在上下文里，块库里根本没有它（还没离开）
② 只有一个版本 —— 冷层里每个事实只有一条链，链上只有一个 head
③ 写入路径只有一条 —— 不需要判"进哪层"
④ 一致性天然成立 —— 因为只有一份
```

**如果要画成三层，正确的是这样（但性质不同）**：

```
L0  上下文       宿主管，我们不读写
L1  块库         我们的全量数据，带链
L2  索引         纯派生，可删可重建
```

注意 L2 是**索引**不是**缓存** —— 索引不存内容，只存"去哪儿找"。
索引坏了重建一次就好，缓存坏了会丢数据。**这是两种东西，别混。**

### 10.5 什么时候才真的需要缓存

不是"永远不需要"，是"在这个位置不需要"。真的需要缓存的是：

```
① 库大到一次全扫不了（几十万块以上）→ 需要 bloom filter / 分片
② 每次检索都调模型（贵且慢）        → 需要结果缓存（key = hash(query)）
③ 跨设备同步                        → 需要本地副本（但那是副本，不是缓存层）
```

我们现在的规模（几百到几万块）**一个文件全扫只要几十毫秒**，上缓存是自找麻烦。

> **一句话：缓存是为了"算不起"，不是为了"记得住"。**
> 我们真正的问题是"想不起来"，不是"算不动"。

## 十一、六条铁律（现在讲原理）

前面所有推导收敛成六条。每条都能从上面找到出处。

### ① 账本唯一真相，块库只是视图

因为**块库可以重建**，所以可以放心地重构、迁移、试错。
一旦账本不唯一，所有"重建"都变成赌博。

**推论：判断只做一次，判完即存档。**
模型的判断不可复现（同样的话问两遍，答案可能不同）。
那就只让它判一次、把结论记进账本，以后**只读账本，绝不重问**。
——这样"不可复现"这个问题，被"判一次"关在门外了。

### ② 卡片永不删

**删不可逆，不翻可逆。** 在可逆和不可逆之间，永远选可逆。

而且"当时不重要"从来不等于"以后不重要"：
用户随口一句"我讨厌香菜"，当时谁也没在意；半年后做饭的时候，那就是最重要的一条。

### ③ 一块只装一件事

因为**静默的错比明显的错贵一百倍**。
压错一次（把两件事合成一块），所有索引都指向那个错误答案，而且不报错。
多一张卡只是多几 KB。**空间是最便宜的，误删和误压是最贵的。**

### ④ 库里只放"已经离开桌面"的东西

这就是第十节的全部结论。
今天说的话在上下文里，不需要任何人再存一遍。

### ⑤ 块是碎片，答案是拼的

因为一块装不下全貌（5.3）。
所以检索不是"找到那条记忆"，是"捞几张 → 聚成线 → 拆成空 → 逐个填 → 拼一句话"。
**拼不齐就说拼不齐，不许编。**

### ⑥ 用户是裁判

```
分数分不开     → 问
并列跨了线     → 问
一个特征都没有 → 说不知道
库里确实没有   → 说不知道
```

**机器负责"找得全、算得快"，人负责"这说的是哪一件事"。**
机器猜错一次，比问一句贵十倍。

## 十二、我用掉的十四种错误

这部分比方案值钱——因为方案是"我选了这条"，而错误是"这条路为什么走不通"。

| # | 试过 | 死因 |
|---|---|---|
| 1 | 关键词检索当主路 | 六种硬伤；最要命的是代词：**"上次说的那个"一个关键词都没有** |
| 2 | 固定长度坐标（256 bit 位串） | 特征种类会超过位数，扩位等于全库重算 |
| 3 | 字面 n-gram 概念扩散 | **3/12**：`兵七进一` 和 `炮二平五` 一个字都不重合 |
| 4 | 纯共现聚类 | 上位词根本不在语料里——"象棋"这两个字那天一次都没出现。统计能长树叶，长不出树枝 |
| 5 | 随机编号当主索引 | 看编号不知含义，改分类要全库重排 |
| 6 | **三级缓存（L1/L2/L3）** | 上下文本身就是 L1+L2；降级=删；三层各存一个版本，不知道信哪个（第十节） |
| 7 | `value = score/√token` 选块 | 平均块 191 → **43 token**，预算只花 41%，选出的 6 块全不相关 |
| 8 | 卡片生命周期（降级/合并/墓碑） | 删不可逆，不翻可逆 |
| 9 | 链式传播（A→B→C） | 会雪崩、无法收敛 → 换广播（只标"有新情况"，不改关系） |
| 10 | 全靠规则判"是不是同一件事" | 真实口语只能判 **16.9%**（66.6% 的句子没有主语） |
| 11 | 隐私一律整块打码 | 打多了答案就残了——问订单号答不出来 |
| 12 | 每轮实时建块 | 一天 345 块 / 12 万块一年，碎到没法用 |
| 13 | 绝对阈值判"有把握" | top8 差 **0.001** 却全部越过 0.55 |
| 14 | 按序号打破并列 | 最早的块永远赢——一个完美的时间偏置 |

**还有一条系统级的**：

> **结构复杂度和脆弱度成正比。**

所以我给自己定了三条反向纪律：

```
能砍就砍 —— 一个机制三个月没发挥作用，砍掉
能浅不深 —— 分类到"科"够用，就别下到"属"
能不做就不做 —— 加一层之前先问："不加会怎样"
```

（第十节的三级缓存，就是被第一条砍掉的。）

## 附录 A · 接入检查：最常见的失败不是"记不住"，是"只存不用"

真实案例（2026-10-29，跑了两天的库）：块数一直在涨（347 → 366），
但回复里一个字都没用上 —— 因为**建块/检索那个模块压根没被加载**。
内置清单里漏了一行，块库就成了只会写、不会读的摆设：数据很漂亮，人还是失忆。

**接入完必须验四件事，一条都不能跳：**

```bash
① 库在长          node src/cli.mjs stats        # 块数在涨
② 索引对得上       node src/cli.mjs rebuild      # 重建后块数、内容哈希不变
③ 检索真能命中     node src/cli.mjs search "上次那杯奶茶多少钱"
④ 注入真进了提示词  在你的宿主里把一轮完整系统提示词打出来，搜一下块里的原话
```

**第 ④ 条最关键，也最容易被跳过：「库里有」和「模型看见了」是两件完全不同的事。**

还有一条：**别双份注入。** 老的关键词记忆和新块库同时往提示词里塞，
同一件事出现两遍会互相稀释。留一个 —— 要么关掉老的召回段，要么只把新库当"翻查工具"。
