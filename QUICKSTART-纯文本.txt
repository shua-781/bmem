【任务】给这个 AI 装一套长期记忆（块库架构）

你是有文件读写和命令执行权限的 agent。

零、先理解这是什么，再动手（这段最重要，别跳）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

这不是向量检索，不是 RAG，也不是"把对话摘要压缩后存起来"。
这三种是最常见的 AI 记忆做法，这套东西全都不用。原因：

· 向量检索查不准口语：同义词、语序、代词、隐式表达都糊。
  最要命的是代词——"上次说的那个"连一个关键词都没有，
  向量也只能给你一堆"看起来像"的东西，而它要的是"就是那件事"。

· 摘要压缩压扁了细节就找不回来。而"上周那杯奶茶 19 块""他生日 12 月 8 号"
  这种细节，恰恰是用户最会追问的地方。

· 一个不断"合并相似记忆"的库，等于一直在删。
  合并是删的近义词，而删不可逆。

那它是什么：一个"卡片档案室"。

  上下文 = 桌子。今天聊的东西都摊在上面，桌子满了就得收走。
  块库   = 档案室。收走之前，把那张纸做成卡片收起来。
  账本   = 只追加的日志。唯一真相；档案室坏了靠它重放重建。
  索引   = 卡片目录。纯派生，删了可以重建。
  档案员 = 每天夜里跑一次的 AI。判断"这几段是不是同一件事"。

三个最反直觉的地方（绝大多数实现会在第一步就走反）：

1. 什么时候建卡：不是"每聊一句就记"，是"内容要离开桌子的那一刻"。
   每轮都建 = 一天几百张碎卡，碎到没法用。

2. 卡片永不删：不降级、不合并、不建墓碑。
   理由只有一句：删不可逆，不翻可逆。空间最便宜，误删最贵。

3. 答案是拼的，不是找的：一张卡 100 多 token，装不下一件事的全貌。
   要抽 12~20 张 → 按同一件事聚成一条线 → 拆成"要答的几个空" → 逐个填。
   填不齐就问用户；一块都没有就说"我不记得"。

【块】blocks.json 里的一条
  coord        位置 ID，永不变，纯序号无语义，如 "1-1-42"
  ver          第几版
  content      摘要 150-250 字，必须保留结论
  features     概念名数组（只存名字，不存编号）
  topic        "主实体|谓词|宾语"，判断"是不是同一件事"用
  gate_main    主分类（自己定一套，如 R人际 T技术 L生活）
  gate_sub     副分类数组
  result       结论/状态，必填
  confidence   high=用户原话直引 / mid=模型压缩 / low=推测
  line_id      同一件事的多块共享
  origin       这条链从哪开始
  origin_at    这件事最初发生的时间（覆盖时不许改）
  created_at   这一版内容诞生时间
  head         这条链最新的那块
  prev         上一版
  kind         ROOT / OVERWRITE / REBUILD
  source       dialog / user / reflection
  source_id    幂等键（同一来源只建一次）
  tokens       估算 token 数
  content_hash 完整性校验用

【事件】events.jsonl 每一行
  seq        全局单调递增（不是每个会话各自从 0 数！）
  ts         UTC+8 到秒，如 2026-10-27T20:15:03+08:00
  type       BLOCK_WRITE / BLOCK_OVERWRITE / BLOCK_REBUILD
             / BROADCAST / PROPOSAL / PROPOSAL_DECIDED
  coord      货位号
  payload    全字段；覆盖类必须同时存旧内容和新内容
  prev_hash / hash   链式哈希

【时间】四类分开，绝不许都叫"时间戳"
  created_at   这一版内容诞生
  origin_at    这件事最初那句（覆盖时不许动）→ 算"多久以前"用它
  assigned_at  这一版入库时间
  一律 UTC+8 到秒；禁止存本地时间、禁止存"几分钟前"

四、施工顺序（不许跳）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【第 0 步 · 修前提】半天，必须先做
  □ 事件日志加"全局单调 seq"
  □ 事件加 session 标识
  □ 建 topic 索引（topic → [coord]）
  □ 跑一次：重放两遍，库的 (coord, ver, hash) 集合一致
  为什么必须先做：整套安全性建立在"账本能重放"上。
  seq 不全局单调 = 重放顺序错 = 全部白搭。

【第 1 步 · 存储层 store.js】
  toISO / fromISO / dayOf          时间换算
  appendEvent(ev)                  只追加，永不整文件重写
  readEvents()
  loadBlocks / saveBlocks          原子写：临时文件 + rename
  loadSlots / saveSlots
  nextCoord(slots)                 位号只增不减、永不复用
  rebuildIndexes(blocks)           全量重建 8 张索引

【第 2 步 · 写层 write.js】
  addBlock({content, features, topic, source, source_id, at})
    → {ok, coord, kind}

  判定逻辑（判不准一律新开）：
  1. 幂等：source_id 已存在 → 直接返回旧 coord
  2. 找同 topic 的 head
  3. 找到 → 算特征重合度 Jaccard
       ≥ 0.5 → 覆盖：ver+1，prev 指旧版，head 指自己，origin_at 不变
       < 0.5 → 新开：新 coord，origin/line_id 继承，旧块 head 改指新块
  4. 找不到 → 新开（kind=ROOT）

  每一步都要先写事件，再写库。

【第 3 步 · 读层 read.js】核心，照这个来

  score = w1*f1 + w2*f2 + w4*f4     权重先取 0.3 / 0.5 / 0.2
  f1 = 分类命中（主分类 1.0，副分类 0.4）
  f2 = Σidf(查询特征 ∩ 块特征) / Σidf(查询特征)
       ★ 分母永远用查询侧，不用并集
  f4 = exp(-距今天数 / 7)           ★ 距今用 origin_at，不是 created_at

  四个必守细节（每个都踩过坑）：
  ① 可用性铁律：f2 = 0 的块一律不许进上下文
     分类对了但一个字不沾 → 会挤掉真正相关的块
  ② 某因子恒为 0 时必须重新归一化权重
     新库还没有"关系权重"，别让它白吃 0.15
  ③ 泛词过滤：df/N > 0.15 的词不算主题，是背景词
     实测：问"光发表情什么意思"，"表情"命中 69/347 块
     → 注入一整段表情包记忆 → AI 跟着只发表情
  ④ 槽词不进特征：「几点」「多少钱」「哪里」是"要答的空"，不是主题

  选块：
  1. 候选 = 精确特征命中 ∪ 分类命中
  2. 按 score 排序
  3. 并列（分差 < 1e-9）→ 随机取，随机种子 = hash(查询文本)
     既随机又可复现，且不会让最早的块永远赢
  4. 多抽：K = 12~20 块，直到 token 预算满（2500~3000）
  5. 单块上限：一块超过预算 30% → 截断注入

  出口四态（三层判据，必须串联，不许并联）：
  第1层 分得开吗：margin = score(top1)-score(top2) ≥ 0.08
                  且 top1/top2 ≥ 1.10
  第2层 分不开：并列的块是不是同一件事？（最大线占比 ≥ 40% → 是）
  第3层 槽齐吗：查询要的槽（是否/数量/时间/地点/型号）逐个填

  全过+槽齐    → 答全：拼成一句话，说明"这几轮拼的"
  缺槽/跨线     → 答+问：先答确定的，明说缺什么，然后问用户
  坏并列/抽空   → 问：不许自己挑
  确实没有      → 不编：说"我不记得"

  拼装规则：同一 line_id 的块按 origin_at 排成一条线；
  ★ 填充不许跨线借词（把 A 事的数字填进 B 事的句子，是最危险的错法）

【第 4 步 · 挂载层 index.js】
  □ 注入钩子：拿用户最新一句 → contextFor(句子) → 返回一段提示文本
     （不注入就返回空字符串）
  □ 定时器：每 5~10 分钟把外部记忆源的新条目搬进块库
     （幂等，按 source_id 去重）
  □ 只读接口：/stats /search?q= /rebuild /sync
  □ 启动自检：块数、词表大小、索引是否就绪
  □ ★ 全部 try/catch 包住：记忆出错绝不许影响正常聊天

【第 5 步 · 批处理 nightly.mjs】
  ① 抽候选：把"要离开上下文"的那段切成候选（每段带时间、来源）
  ② 落 PROPOSAL 事件（含 input_hash）
  ③ 按话题簇切批（20~40 段/批，别一次喂几百段）
  ④ 调模型判断：{是否同一件事, 拆几段, 每段 topic, 置信度, 原话直引}
  ⑤ 判决落 PROPOSAL_DECIDED（带 input_hash + prompt 版本）
  ⑥ 按判决落库（覆盖/新开）+ 重建索引
  ⑦ ★ 幂等：同 input_hash + 同 prompt 版本已有判决 → 直接复用，
     绝不重跑模型。模型判断不可复现，只判一次、判完即存档，
     就把"不可复现"关在门外了。

地基
  □ 重放两遍，库的 (coord, ver, hash) 集合一致
  □ 删掉 blocks.json，从 events.jsonl 重建，链结构一致

写
  □ 同一段内容写两次 → 第二次被幂等跳过（不是建两块）
  □ 同一件事换个说法写进来 → ver+1，coord 不变
  □ 语义完全不同的事 → 新 coord，旧块内容字节不变，旧块 head 指新块
  □ 一条链上永远只有一个 head（两个 head = 库损坏，报警）

读
  □ 问一句闲聊（如"你在干嘛"）→ 注入 0 字
  □ 问"这件事的细节"（带具体名词）→ 注入相关块，且首块真的相关

  □ 同一查询跑两遍，排序一致（并列用 hash 种子）
  □ 同一件事的很多轮 → 能拼成一句话答出来

安全
  □ 注入文本里不含身份证/密码/密钥（核心隐私打码）
